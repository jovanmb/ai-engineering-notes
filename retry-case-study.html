Case study

An AI reviewer on a retry change that passes every test

Setup. A second run of my pr-review skill, this time aimed at a class of bug that ordinary tests can't see. The PR, "LUM-1060: retry transient API failures", adds automatic retries with exponential backoff to the HTTP client behind my dashboard. It's two files: the client, and five new unit tests. All 43 tests in the repo pass.

I planted one bug: the client retries every method, including POSTs that carry no idempotency key. If the server saves a message but the response is lost (a timeout, or a 502 from a proxy), the client sends it again. The ticket's third acceptance criterion says plainly: "a retried request must never apply a user action twice."

The reviewer was a fresh Claude Code subagent given only the skill file, the trap catalogue, the branch and the ticket. Before it ran, I wrote down what I'd planted, what I already knew, and what it should not flag, so the result couldn't be graded generously after the fact.

Result against the sealed list

Sealed before the run What happened
Planted: retrying unkeyed POSTs sends the message twice ✅ Found and reproduced against the real API: one send, two messages stored. Graded High; AC3 not met
Known to me: retrying a ticket move that already happened gets a 409, so the user sees a failure for a move that succeeded ✅ Found and reproduced
Correct on purpose: comment retries reuse their idempotency key; 4xx responses aren't retried ✅ Correctly not flagged. It checked both and said why they're safe
Not on my list 🆕 A real bug I wrote without noticing: the 8-second timeout is cleared as soon as the response headers arrive, so a server that stalls mid-body leaves the request hanging forever, with no error and no retry. Reproduced: still pending after 2 seconds on a 200 ms timeout

It also checked, and correctly did not raise, the cases that only look dangerous: replaying a PUT of a whole document is harmless, a replayed DELETE gets a 404 the code already ignores, and the "scheduled message" endpoint stores nothing in this codebase, so the duplicate can't be shown there.

I reran each of its reproduction scripts myself before writing this up.

What it got wrong

It didn't spawn refute subagents. The skill only required them for money, security and auth findings. The blocking finding here was data integrity, so the reviewer reproduced it instead and moved on. The reproduction was solid, but nobody independently tried to argue it down. That's a gap in the skill, not a lapse by the reviewer: it followed the rule as written and then flagged the rule as too narrow.

What changed in the skill (v1.1)

The reviewer listed five ambiguities. Each became an edit:

  1. Refutation now covers data-integrity findings, and any finding that alone forces a ❌. A reproduction proves the defect exists; refuters test whether it's reachable, already guarded or mis-graded. The skill now says to do both.
  2. Exploitability has a defined scale. High is hit in normal use. Medium needs an uncommon but realistic condition. Low needs special access or a condition the deployment doesn't have.
  3. A partially met AC blocks when the missing part is something the AC states explicitly.
  4. Findings are ranked by severity, then by the stated priority order.
  5. "Read-only" is precise. Never change tracked files; build output in ignored paths and scratch scripts outside the repo are fine.

The trap catalogue gained one entry, the stalled-body timeout, because I genuinely missed it. I didn't add a trap for retries on writes. That one was planted, and the catalogue's rule is that an entry earns its place by being missed for real.

Why this matters

A retry layer is the kind of change that gets approved on sight: it's small, the code is tidy, and the tests it ships all pass, because they only test the cases where retrying is safe. The procedure that caught it is mechanical, not clever. Turn each acceptance criterion into a checkable behaviour, build a truth table of method × failure point, and run the cases against the real server instead of reasoning about them.
