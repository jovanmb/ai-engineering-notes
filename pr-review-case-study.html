Case study

An AI reviewer on a PR with a planted bug

Setup. A realistic one-commit PR against the API behind my dashboard: "LUM-1050: add free-text search to GET /api/tickets". It touches five files across the API, the domain and both storage backends. I planted one bug on purpose and told the reviewer nothing about it: the search term is interpolated into SQL (summary LIKE '%${q}%'), and the parameter has no length cap.

The reviewer was a fresh Claude Code subagent given only my pr-review skill file, the trap catalogue, the branch and the ticket's four acceptance criteria. It ran read-only. Nothing below is edited except for length.

What it found

# Finding Planted? Verdict effect
1 SQL injection in the search filter. An ordinary search like doesn't returns a 500, ' OR 1=1 -- bypasses the scope filters, and a UNION reads other tables. Stacked writes are blocked by the driver Yes ❌ blocking (High; exploitability Low on a localhost dev server)
2 The in-browser demo backend silently drops q, so acceptance criterion 4 ("same behaviour on both backends") fails No, a real mistake of mine ❌ (unmet AC)
3 The two backends disagree: SQLite LIKE treats _ and % as wildcards and folds case for ASCII only; the in-memory filter doesn't No Medium
4 No tests for search, apostrophes, search + pagination, or backend parity Partly (I added none) Suggest-only

It proved findings 1 and 3 by running the exact SQL against Node's SQLite, rather than reasoning about them. It also noticed that the seed data's own summaries contain apostrophes, so the bug fires on normal use, not just on attack input.

The refute step, in practice

Because finding 1 is a security finding, the skill required refute subagents. It spawned two, in parallel:

  • A (look for an upstream guard): found none and reproduced the 500, the filter bypass and the UNION read. The finding survives.
  • B (argue reachability): accepted the bug but argued for a downgrade to Medium: the server only listens on localhost, the API is already unauthenticated, and the data is fictional.

The reviewer kept the severity at High and recorded B's points on the exploitability axis instead. The skill grades severity × exploitability and says refutation must never soften a finding that survived. Its reason: the decisive failure (a 500 on a normal search) needs no attacker at all.

What it dropped: a claim that stacked statements could write. It tested this, and the driver only compiles the first statement, so it didn't make the claim. It also left out a pre-existing ordering difference between backends, because that's not in this diff.

What it fed back into the skill

The reviewer listed five ambiguities in pr-review/SKILL.md. Each became an edit, following the skill's own retrospective rule (fix recipe gaps found in a real run):

  1. Severity vs exploitability. Now explicit: reachability arguments lower exploitability, never the severity label.
  2. A refuter that argues for a downgrade rather than a refutation. The finding survives; record the argument under exploitability.
  3. An unmet AC with no current caller. It still counts as unmet. Grade by the AC, and note the missing caller in the impact.
  4. Local branches with no hosting service. Section 0 now covers them: no threads, no ledger.
  5. Which lens owns non-UI client code (a JS data adapter). Architecture and Ticket fit; Frontend is for what the user sees.

Why this matters

The planted bug is the kind a quick review approves: it's one line, it follows the shape of the line above it, and every existing test still passes. The two findings I didn't plant are the more useful result. The procedure (map each AC to behaviour first, check parity across implementations, run the input instead of reading it) found real mistakes in my own change that I'd missed.

The skill is open source. claude-code-pr-review on GitHub, MIT licensed, installable as a Claude Code plugin.
