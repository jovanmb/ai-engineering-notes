Case study

An AI reviewer on a design problem, judged against the codebase

Setup. The third run, and the first through the packaged skeptical-reviewer agent itself, installed the way a user would and run headless in Claude Code. The target was its newest ability: reviewing design against the codebase's own standards, not a textbook.

The PR, "LUM-1070: flag stale tickets on the board", adds one endpoint to the API behind my dashboard. It's three files, and all 39 tests pass. The code works. What's wrong with it is design, and only a reviewer that knows this codebase would see it:

  • the business rule sits in the API layer, though the domain module's header and the README both say rules live once in core/ so the in-browser demo can use them too;
  • it hard-codes a status list the domain already defines;
  • it builds an interface, an abstract base class and a factory for exactly one rule;
  • it calls new Date() where the domain injects a clock for testing.

As before, I wrote down what I'd planted, and what it should not flag, before it ran.

Result against the sealed list

Sealed before the run What the agent did
Rule in the wrong layer, against a documented house rule ✅ Found, but graded too low (see below)
Duplicated status list ✅ Found, with its cost: a new status silently drifts from the board
Interface + abstract base + factory for one rule ✅ Found, and correctly kept as a suggestion: speculative, but no defect today
Bypasses the injected clock ✅ Found and proved: under a fixed clock the endpoint returns 57 tickets instead of the 34 that are stale
Correct choices: input validation, reading every page ✅ Not flagged. It probed 9 invalid inputs and compared every page against an independent oracle
Not on my list 🆕 My own test was weak. It mutation-tested it: made the endpoint read only page 1, changed the default, dropped two statuses. All four mutations still passed. I reproduced the first one myself

Its report opened with Standards applied: the README's architecture section, the domain module's header, the project's decision log, the TypeScript config, the sibling route and the sibling tests. That's the codebase awareness working: it measured the PR's test against the repo's own pagination tests, and quoted the decision-log entry about exactly this bug class.

What it got wrong

1. It inverted the priorities. The skill says breaking a documented house rule is a graded finding. The agent decided the rule was "descriptive, not a must", and let a refuter talk the layering violation down to a suggestion. That also broke the skill's rule that refuters may lower exploitability, never severity. The verdict was still ❌, but it rested on the test gap, while the architecture problem became optional. I'd rank them the other way round.

2. It wrote refuter results before they arrived. By its own account, it drafted the refuters' conclusions while they were still running, then discarded the draft when the real reports came in. It reported this itself, and the final report uses only the real results. But a reviewer that's allowed to imagine its own peer review is the failure this whole procedure exists to prevent.

What changed in the skill (v1.4)

  1. A descriptive rule is still a documented rule. "Business rules live in core" counts as a house standard, including README architecture sections and module header comments. It's graded on its concrete cost and never dropped to a suggestion for its phrasing; must only decides whether it blocks.
  2. The refuter rule covers design findings too: a downgrade argument goes on the exploitability axis.
  3. Never write a refuter's conclusion before its report arrives.
  4. Mutation-check the PR's own tests. The technique it used unprompted is now part of the procedure: break what each new test claims to cover, and if the suite still passes, the test doesn't cover it.

Why this matters

Design review is where AI reviewers are weakest: they either nitpick against textbook principles or wave everything through. This run shows the middle path working: it found all four planted design problems, kept the speculative abstraction as a suggestion, and grounded every point in the codebase's own files. It also shows where it still needed a human: deciding which problem matters most.
