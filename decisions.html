Decision log

Twelve times I corrected the AI

I built this dashboard with Claude Code as the main author of the code, and me as the reviewer, tester and decision-maker. This log records the times the AI's output was wrong, incomplete or risky, how each was caught, and what changed as a result. Every entry is a real event from the build, first in my private version at work and then in this public rewrite.

The pattern that matters: most of these bugs looked correct. The page rendered, the button responded, the tests the agent first wrote passed. They were caught by checking behaviour against reality, not by reading the code.

1. A silent page limit picked the wrong "current ticket"

What the agent built: "Working on now" chose the most recently updated In Progress ticket from the sprint query.

What went wrong: the sprint grew to 151 tickets, but the query asked for one page of 100, ordered by board rank. My two most recent tickets were on page 2, so the card confidently showed an older ticket from outside the sprint. Nothing errored.

How it was caught: I said "it still shows the wrong ticket". Instead of tweaking the selection rule, I had the agent count the sprint (151), check which page my tickets were on (page 2), and confirm the tracker's page cursor worked before relying on it.

Fix: my own tickets now come from a dedicated query (about 16 rows, so always complete), and the whole-sprint board follows the cursor to the end. In this repo the API's pagination is covered by tests in memory and on SQLite, and the seed deliberately has over 100 tickets so the bug can't hide.

Lesson: any list from an API has a page size, whether you asked for one or not. "Most recent X" over a truncated list is a wrong answer that looks right.

2. Multi-line Slack messages were cut to their first line

What the agent built: a regular expression to pull the message text out of the Slack search result.

What went wrong: in multiline mode, $ matches at every line end, and the lazy group stopped at the first one. Every multi-line message (daily-sync posts, long DMs, PR notes) showed only its opening line, "Blockers:".

How it was caught: I noticed a daily-sync preview that couldn't possibly be one line long.

Fix: take everything after Text: up to the result's closing ---, explicitly. There's now a regression test (web/test/lib.test.mjs).

Lesson: regex flags change what anchors mean. Test parsers on the hardest real input, not the first example.

3. A shared confirm helper left four buttons stuck

What the agent built: a two-click confirm (armed()) for every outward action, because the sandboxed page can't use confirm().

What went wrong: after the second click, the label stayed on "Confirm…" forever. That affected Jira moves, Jira comments, Slack replies and scheduling the daily sync, since all four shared the helper.

How it was caught: a Playwright test of the new Jira panel checked the button label after a successful move.

Fix: restore the original label before running the action. One fix in the shared helper corrected all four buttons.

Lesson: a bug in a shared helper is a bug everywhere it's used. When a test catches one, find every caller.

4. "Refresh" refreshed nothing

What the agent built: a Refresh button that cleared the runtime's cache and showed a toast.

What went wrong: clearing the cache doesn't re-run anything; the next poll would, a minute later. In the real viewer the toast could also render below the visible area, so the button looked dead.

How it was caught: I reported "refresh does nothing". A Playwright run showed the handler firing, so the bug was in what it did, not whether it ran.

Fix: Refresh re-runs every live query and reports on the button itself ("Refreshed 10:38", or "3 of 5 refreshed").

Lesson: "it runs" and "it works" are different checks. Feedback belongs where the user is looking.

5. The wrong signal decided what I was working on

What the agent built: "Working on now" took the ticket from the checked-out git branch first.

What went wrong: my main checkout sat on an old branch while the real work happened in other worktrees, so the card was stuck on a finished ticket. When fixed to use other signals, it still happily showed tickets that were with QA or in UAT.

Fix: a ranked set of signals: my explicit pick, then today's daily-sync plan, then my latest In Progress ticket, then the branch. The card says which one it used, and only In Progress tickets count. A pick that moves on to QA folds into one line instead of pretending.

Lesson: a heuristic needs to say where its answer came from, and the user needs a way to overrule it.

6. Mentions were flooded by bots

What went wrong: the Mentions search returned Jira, CI and deploy notices, because bots mention you too.

Fix: drop bot messages at parse time, for every chat panel. Tested.

7. A storage check hid features it didn't need to

What the agent built: the page turned off its store unless an "is this the owner?" check said yes.

What went wrong: in some views that check doesn't answer, so the ticket picker and focus list disappeared for the actual owner.

Fix: rely on the store's own server-side rules (owner-only), which already enforce the same thing, and degrade to browser storage when the store is missing.

Lesson: enforce access where the data lives, not by hiding UI.

8. An API token couldn't do what the docs implied

What happened: the Bitbucket token returned 403 on the "who am I" endpoint, then 400 when filtering pull requests by display name.

Fix: derive the account id from my newest merged PR in local git history ("Merged in …(pull request #N)"), look that PR up, and cache the id. That's in laptop/prs.cjs.

Lesson: probe permissions with read-only calls before designing around an endpoint.

9. Escaping broke edits in a way the syntax check couldn't see

What happened: the agent applied some edits through inline shell scripts. A \b in a regex became a literal backspace character, and a \d lost its backslash. The file still parsed, but the regex silently matched the wrong thing.

How it was caught: the title-casing output looked wrong; cat -A showed ^H in the source.

Fix: write edit scripts to files, or use exact-match edits, never inline heredocs with escapes.

Lesson: "it parses" is not "it's right". Look at the bytes when output is odd.

10. Tests written to the wrong expectation

What happened (this rewrite): two new tests expected bot messages to be flagged and kept. The code drops them on purpose (entry 6). The tests failed.

Decision: I checked which behaviour was intended before touching anything, then fixed the tests, not the code. The test now states the reason.

Lesson: a failing test is a disagreement between two pieces of intent. Decide which one is right; don't just make the red go away.

11. Normal behaviour shouldn't look like errors

What happened (this rewrite): the page reads several optional documents on load (a pinned ticket, saved panels). Missing ones returned 404, so the browser console filled with red. Harmless, but it's the first thing a reviewer sees.

Fix: GET /api/store/:collection?id= answers 200 { items: [] } for "not there yet"; the REST GET /:collection/:id still 404s. On GitHub Pages the page no longer probes for an API that can't exist.

12. Things I chose not to build

  • A laptop task runner driven from the web page. I wanted to start Claude Code tasks from the dashboard. My organisation had disabled the official feature for that (Remote Control) by policy, and a polling runner would have quietly recreated it. I didn't build it. The page offers "Let's investigate" instead, which opens Claude Code locally with a prompt, so I start the work myself.
  • Customer text in links. The "Let's investigate" link carries only the Slack permalink, sender and channel. Message text (which can hold customer details) never goes into a URL or browser history.
  • One-click writes. Every Jira or Slack write takes two clicks, warns when the ticket isn't mine or when a move hands it to QA, and refuses to post an AI draft that still contains a [check: …] placeholder.
  • Retries that double-post. Comment writes carry an idempotency key. A retry after a timeout replays the first result instead of posting twice (core/domain.ts, tested).
